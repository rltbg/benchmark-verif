# sha256 — Creusot contre Verus

Fichiers : `impls/rust/src/sha256.rs` (+ `impls/rust/verif/bench_rust_rlib/sha256/`), `impls/rust-verus/src/sha256.rs`.
Journaux : `runs/sha256-creusot.csv`, `runs/sha256-verus.csv`.

## Cible et résultat

Cible : « le condensé exécutable égale une fonction logique SHA-256 (compression, bourrage) écrite dans la logique ».
**Atteinte dans les deux outils**, avec la même structure de spécification :

* `sha256(msg: Seq<u8>) -> St` : SHA-256 de FIPS 180-4 sur une séquence d'octets **quelconque** — bourrage (`pad_byte`,
  `pad_word` : message, 0x80, zéros, longueur 64 bits big-endian), découpage en blocs (`block`), échéancier (`sched`,
  récursif), ronde (`round`), 64 rondes (`rounds`, récursif), compression (`compress_l` / `compress_spec`),
  enchaînement des blocs depuis l'IV (`sha_state`).
* `gen_msg(base, n)` : le message du workload (octet i = octet i mod 8, petit-boutien, de `mix64(base + i/8)`).
* `digest(base, n)` garantit `st_of(result) == sha256(gen_msg(base, n))` ; `run` garantit que le checksum est le
  repliement `ckfold` de ce condensé logique. Absence de panique/débordement et terminaison prouvées partout.

Le code exécuté est celui de `rust-plain` (mêmes boucles, tampon de 128 octets pour la queue, rotations écrites en
décalages et compilées en `ror`) ; seules différences de forme : `compress`/`load_block` `#[inline(always)]`, petites
fonctions `load_be32`/`store_be32`/`pad_tail` (inlinées). Pas d'allocation ni de copie ajoutée.

**Checksums vérifiés** (les deux binaires) : n = 0, 1, 63, 64, 100000, 10^6, 2·10^7 = valeurs de
`spec/checksums.d/sha256.json` ; 55, 56, 65, 119, 120, 127, 128, 1000 identiques entre Creusot, Verus et `rust-plain`.
Performances (min de 5–6 exécutions, machine chargée par d'autres agents, n = 2·10^7) : plain ≈ 102–107 ms,
Creusot ≈ 101–108 ms, Verus ≈ 115–125 ms (Verus compile avec sa propre chaîne 1.99.1 ; le même source Creusot
compilé en 1.99.1 a montré la même dispersion, l'écart semble venir du compilateur/bruit, pas du code).

Comptage : script heuristique sur les lignes non vides hors commentaires ; *spec* = fonctions `#[logic]`/`spec fn` à
valeur + `requires`/`ensures` ; *preuve* = lemmes, `invariant`/`variant`/`decreases`, `proof_assert!`/`assert`,
`snapshot!`/`ghost`/blocs `proof` ; *exec* = le reste (signatures comprises). Le formatage `verus!` est plus vertical.

## Ce qui a coûté le plus

**Creusot** (fait en premier, il a essuyé les plâtres de la conception) :
1. *Pas de conversion `Int → u64` en logique* (`as u64` refusé sur `Int`, pas de `of_int` exposé) : il a fallu définir
   `u64_of` par récurrence et prouver le lemme `u64_of_view` (`u64_of(v@) == v`) par induction.
2. *Matching loop* : la définition récursive ouverte de `u64_of` (axiome `u64_of x = … u64_of (x-1)`) faisait
   s'épuiser les solveurs sur des buts triviaux ; corrigé en la fermant dans un sous-module (`conv`) qui n'exporte que le lemme.
3. *Invariant de type des tableaux perdu à travers les boucles* : les buts « type invariant » de `h: [u32; 8]`
   échouaient (sans contexte affiché) jusqu'à l'ajout explicite de `h@.len() == 8` dans les invariants.
   Diagnostic long : `-x` n'affiche le contexte que pour certains échecs et seulement sous tty ; il a fallu générer
   `why3session.xml` (`--why3session`) et le lire avec un script, puis `-X` pour voir la tâche.
4. Hors `#[bitwise_proof]`, les opérations bit à bit sont non interprétées ; les casts passent par
   `of_int(t'int …)` : les lemmes octet ↔ mot (`le_bytes_bswap`, `be_word_split`, `byte_le_shift`) doivent être isolés
   en mode `bitwise_proof`, et formulés pour coïncider *syntaxiquement* avec le code (le décalage `8*q` calculé à
   l'exécution ne se ramenait pas à `mul 8 q`).
5. Découpage de `digest` (fonction `pad_tail`, module `compression` qui ferme `compress_l`) pour réduire le contexte.

**Verus** : la structure était connue (traduction de la version Creusot). Coûts : `final(x)` obligatoire dans les
postconditions `&mut` (nouvelle syntaxe de cette version), un `forall` arithmétique sans déclencheur refusé à la
compilation (remplacé par une fonction `word_at` servant de déclencheur), et `(8w+r)/8 == w` qui demande le lemme
`lemma_fundamental_div_mod_converse` de vstd. Le reste — y compris `compress` (64 rondes) et `digest` — est passé
du premier coup : les entiers machine sont des `int` bornés, donc pas de pont Int/vecteur de bits à construire.

## Messages d'erreur

* Creusot : « proof failed » avec la ligne de la fonction (souvent le `#[ensures]` ou la fonction entière) et
  `✘ (a/b)` ; pour savoir *quel* sous-but échoue il faut la session Why3 ou `-x/-X`. Les erreurs Rust/pearlite
  (`<==>` inexistant, `@` hors `pearlite!`, cast `Int as u64`) sont claires.
* Verus : le message pointe l'assertion, l'invariant ou la postcondition précis ; erreurs de déclencheurs et de
  modes signalées à la compilation avec la ligne. Nettement plus rapide à exploiter.

## Ce qu'un modèle plus faible aurait probablement raté

* Creusot : deviner que l'échec de buts *triviaux* vient d'une boucle d'instanciation (et non du but), fermer une
  définition récursive dans un module, et ajouter l'invariant de longueur d'un tableau que l'outil ne propage pas ;
  savoir extraire la liste des sous-buts échoués (session XML) au lieu de modifier le code à l'aveugle.
* Les deux : écrire une spécification *indépendante du code* (FIPS sur une séquence quelconque + `gen_msg`), plutôt
  qu'une « spécification » qui recopie la boucle exécutable ; poser les bons lemmes octets ↔ mots en mode bit à bit.
* Verus : l'instanciation correcte des lemmes (un lemme appelé avec le mauvais argument « passe » mais ne sert à rien —
  cela m'est arrivé sur `stream`).
